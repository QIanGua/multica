---
title: Remote MCP Plugins
description: Declare, configure, approve, and run remote MCP tools through Multica's task-scoped broker.
---

Remote MCP Plugins let a Plugin declare access to tools hosted by a remote MCP
server. The package is declarative: it contains the maximum tool intent and
endpoint host policy, while every workspace owns its endpoint, public settings,
encrypted credential, failure policy, and explicit tool approval.

Enable both `plugins_v1` and `remote_mcp_plugins_v1`. Private packages also
require `private_plugins_v1`. The feature flag gates setup and new resolution;
administrators can still revoke credentials, disable Bindings, and uninstall an
existing Plugin while the Remote MCP flag is off.

## Manifest contract

Use `plugin init` to generate a manifest-only package:

```bash
multica plugin init ./remote-tools \
  --contribution remote-mcp \
  --endpoint-host mcp.example.com \
  --key dev.example.remote-tools \
  --name "Example Remote Tools" \
  --publisher example.internal
multica plugin validate ./remote-tools
```

`tool.remote-mcp.v1` requires the `tool.remote-mcp.connect` capability and the
`execution-manifest-v1` plus `remote-mcp-v1` daemon features. V1 supports only
MCP Streamable HTTP over public HTTPS, with protocol versions `2025-03-26` and
`2024-11-05`. A contribution declares:

- an exact or wildcard HTTPS host policy;
- the maximum tool names and their `read` or `write` risk;
- an optional JSON object schema for non-secret public configuration.

Endpoints and credentials never belong in the package. Unknown fields,
undeclared capabilities, unsafe hosts, unsupported transports, duplicate tool
names, or malformed schemas fail validation. See
`examples/plugins/remote-mcp-fixture` for a complete reference Plugin with one
read and one side-effecting write tool.

## Configure, discover, and approve

Install the Plugin disabled, then configure each Remote MCP contribution in
**Settings → Plugins**. Owners and admins can enter the endpoint, choose no
authentication, a bearer token, or a custom header, and select a failure policy.
The credential input is write-only; after save, the UI shows only configured,
missing, or revoked state and a safe hint.

The Server connects to the endpoint and discovers `tools/list`. Review the
discovered names, descriptions, risk labels, and input schemas, then explicitly
approve the desired subset. Multica stores an append-only configuration revision
with canonical schemas and a toolset digest. A Plugin cannot be enabled until
every Remote MCP contribution has a reviewed revision and any required
credential is active.

The same lifecycle is available from the CLI. Pass secrets only through stdin
or a file, never as an argument:

```bash
printf '%s' "$REMOTE_MCP_TOKEN" | multica plugin remote-mcp configure \
  <installation-id> <contribution-key> \
  --workspace acme \
  --endpoint https://mcp.example.com/mcp \
  --auth-type bearer \
  --credential-stdin \
  --failure-policy required

multica plugin remote-mcp test <installation-id> <contribution-key> --workspace acme
multica plugin remote-mcp approve <installation-id> <contribution-key> \
  --workspace acme --tool search --tool create-item
multica plugin remote-mcp revoke <installation-id> <contribution-key> --workspace acme
```

Changing an endpoint, public configuration, credential, or Plugin version makes
the connection unreviewed. Re-run discovery and approve the tools again. Upgrade
and rollback keep immutable release and configuration revisions; tasks already
claimed retain their pinned snapshot, while new tasks resolve the current
reviewed revision.

## Runtime boundary

At task claim, the Server resolves the effective Plugin Bindings and produces an
immutable Execution Manifest. It pins the installation, release, contribution,
configuration revision, endpoint policy, approved tool schemas, schema digest,
and failure policy. The stored manifest contains only an opaque credential
reference—never plaintext secret material.

The daemon resolves the task-scoped connection, re-discovers tools, and fails
closed if an approved tool disappeared or its input schema changed. It then
starts a loopback-only broker on a random capability URL. Codex, Claude, Hermes,
and Qoder receive that local URL; they never receive the upstream endpoint or
credential. The broker:

- injects credentials only on the upstream request;
- exposes only the reviewed tool allowlist;
- rejects unapproved tool calls before making a network request;
- denies redirects, proxies, DNS rebinding to private ranges, non-HTTPS URLs,
  oversized bodies, excess concurrency, and excess calls;
- uses bounded connect/call timeouts and does not retry side-effecting calls;
- closes when the task ends and logs task, installation, contribution, tool,
  duration, and sanitized result class without arguments or secrets.

`required` connections stop the task before provider launch when startup
validation fails. `optional` connections are omitted and reported in explicit
degraded diagnostics so the task may continue without those tools.

## Security and operations

Set `MULTICA_PLUGIN_SECRET_KEY` to a dedicated key. The Server refuses to use a
plaintext fallback. Stored credentials are workspace- and installation-scoped,
versioned, encrypted at rest, redacted from API responses and logs, and resolved
only for an authorized task claim. Revoking a credential disables the
Installation for new work; reconfiguration and approval are required before it
can be enabled again.

Watch daemon logs for `Remote MCP broker call` audit events and task diagnostics
for optional startup degradation. The health shown in Settings reflects Plugin
lifecycle state; use **Test connection** to check the current reviewed endpoint
and credential without enabling a Binding.

## Troubleshooting and V1 limits

- **Endpoint rejected**: use a public HTTPS URL inside the manifest host policy.
  Localhost, private/link-local/metadata addresses, redirects, URL credentials,
  query strings, and fragments are rejected.
- **Approval required**: configure or test again, review the returned schemas,
  and approve at least one declared tool.
- **Schema drift**: inspect the upstream change, then create and approve a new
  configuration revision. Multica will not silently accept drift.
- **Credential missing or revoked**: configure a replacement credential, test,
  approve, then re-enable the desired Binding.
- **Provider incompatible**: V1 supports Codex, Claude, Hermes, and Qoder.
- **Task stopped before launch**: inspect whether a required connection is down;
  use `optional` only when running without the tools is semantically safe.

V1 does not support local stdio MCP servers, SSE-only legacy transport, OAuth
flows, dynamic client registration, browser-based consent, credential sharing
between Installations, automatic approval of new or changed tools, arbitrary
upstream headers, or retries of tool calls.
