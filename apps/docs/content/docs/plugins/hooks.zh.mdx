import { Callout } from "fumadocs-ui/components/callout";

hook 是由**你**实现的一项能力。当成员、智能体或产品事件需要它时，Multica 会用带签名的 `POST` 调用你的接口。这是 Multica 唯一向外调用的方向，所以围绕它的每项检查都针对目标地址。

## 如何声明

```json
{
  "key": "triage_issue",
  "name": "对这个任务做分诊",
  "description": "把任务标题和描述发给我们的分诊服务，并把建议的负责人和优先级作为评论写回。",
  "input_schema": {
    "type": "object",
    "properties": { "reason": { "type": "string" } }
  },
  "triggers": ["ui", "manual", "event"],
  "events": ["issue.created"],
  "transport": { "type": "http", "url": "https://hooks.example.com/triage" },
  "timeout_ms": 8000
}
```

transport URL 必须是 HTTPS，其主机必须被某个 `net:` scope 精确覆盖。这在解析 manifest 时检查一次，拨号时再检查一次。

## 四种触发方式

一个 hook，最多四个调用点。声明某种触发方式意味着**谁可以调用它**，而不是它做什么。

| 触发方式 | 发起者 | 阻塞 | 回调写入归属 |
| --- | --- | --- | --- |
| `ui` | 你的 surface，经 `multica.hooks.invoke()` | 仅该面板请求 | 点击的人 |
| `manual` | 成员，从任务操作菜单或命令面板 | 仅该菜单操作 | 选择的人 |
| `agent` | 把你的 hook 当工具调用的智能体 | 仅该次工具调用 | 该智能体 |
| `event` | Multica，在产品事件发生时 | 从不 | 插件自身 |

`manual` 的菜单条目由 Multica 渲染，不由你渲染——这个列表归宿主所有，因为触发方式决定了写入以谁的名义发生。列表也不会按"这次调用能不能成功"来过滤：把接口挂掉的操作藏起来，会让同一个任务上的两个人看到不同的菜单，却没有任何解释。真正被拒绝时，拒绝本身会解释原因。

`event` 派发到工作线程池，从不阻塞产生该事件的请求。它也是唯一会重试的触发方式。

<Callout type="info">
客户端无法凭空发明触发方式。`POST /api/v1/plugin/hooks/{key}` 只接受 `ui` 和 `manual`；`event` 由宿主派发、不接受请求，`agent` 走 MCP 进来。若在这里接受这两者，就等于让浏览器驱动一个本应携带另一种身份的调用点。
</Callout>

## 请求

```http
POST /triage HTTP/1.1
Content-Type: application/json
User-Agent: Multica-Hooks/1
X-Multica-Timestamp: 1755676800
X-Multica-Signature: v1=7f0c…
X-Multica-Plugin-Installation: 6f1e2d3c-…
```

```json
{
  "version": 1,
  "hook_key": "triage_issue",
  "trigger": "event",
  "event_type": "issue.created",
  "workspace_id": "8c1e…",
  "installation_id": "6f1e…",
  "issue_id": "2b7a…",
  "actor": { "type": "plugin", "id": "6f1e…" },
  "input": { "reason": "手动重查" },
  "config": { "team": "platform" },
  "callback_token": "mpc_…",
  "callback_url": "https://multica.example.com/api/v1/plugin"
}
```

| 字段 | 出现时机 | 说明 |
| --- | --- | --- |
| `version` | 总是 | `1`。这个协议刻意保持小而稳定。 |
| `hook_key` | 总是 | 被调用的是哪个 hook。 |
| `trigger` | 总是 | `ui`、`manual`、`agent` 或 `event`。 |
| `event_type` | 仅 `event` | 触发的是哪个事件。 |
| `workspace_id`、`installation_id` | 总是 | 标识该安装。可作为你自己的租户键。 |
| `issue_id` | 有任务时 | 已由宿主解析并做过权限校验。 |
| `actor` | 总是 | `{ "type": "member" \| "agent" \| "plugin", "id": "…" }` |
| `input` | 有传入时 | 原样转发。请校验它——`ui`/`manual` 场景下它来自浏览器。 |
| `config` | 有配置时 | 该安装的**非 secret** 配置。 |
| `callback_token`、`callback_url` | 回调启用时 | 见[回调](#回调)。 |

<Callout type="warn">
优先用 `issue_id`，而不是 `input` 里的任何东西。前者由宿主解析并校验过权限；客户端提供的 id 不该被 handler 信任，而 `event` 场景下根本没有客户端。
</Callout>

### 为什么 `config` 在请求体里，而 secret 不在

你的 handler 没有别的途径读取 `admin` 在配置表单里填的内容——Action API 刻意没有配置接口。secret 类型的字段永远不会包含在内：那是**你**访问**自己**服务的凭证，你本来就有，把它放到网络上等于把每个值交给持有该接口的人。

## 验签

签名是对"时间戳 + 一个字面量 `.` + **原始请求体**"做 HMAC-SHA256，十六进制编码：

```
signature = HMAC_SHA256(secret, timestamp + "." + rawBody)
```

请求头带方案版本：`X-Multica-Signature: v1=<hex>`。密钥是 `admin` 在 **设置 → Plugins** 轮换插件 token 时与安装 token 一起只展示一次的 `whsec_…`。使用前去掉 `whsec_` 前缀并做十六进制解码。它由部署密钥派生，对一个安装是稳定的。

正确的 handler 会做四件事：

1. **先对原始字节验签，再解析。** 先反序列化再重新序列化去验签，是让合法签名验不过、非法签名验得过的经典错误——键顺序和空白都不会被保留。
2. **检查时间戳。** 它在签名内部，所以被截获的请求会过期。Multica 的容差是前后各 5 分钟。
3. **用常量时间比较。** 逐字节比较会泄露"猜对了多少"，这足以还原剩下的部分。
4. **在时间窗内记住已见过的签名。** 这是宿主替你做不了的部分。时间戳把重放限制在几分钟内，只有接收方能通过拒绝重复字节把这个缺口彻底关掉。

```js
import { createHmac, timingSafeEqual } from "node:crypto";

const TOLERANCE_SECONDS = 5 * 60;
const seen = new Map();

export function verify(rawBody, headers, secret) {
  const timestamp = headers["x-multica-timestamp"];
  const presented = String(headers["x-multica-signature"] ?? "").replace(/^v1=/, "");
  if (!timestamp || !presented) return "缺少签名头";

  const drift = Math.abs(Math.floor(Date.now() / 1000) - Number(timestamp));
  if (!Number.isFinite(drift) || drift > TOLERANCE_SECONDS) return "时间戳超出窗口";

  const key = Buffer.from(secret.replace(/^whsec_/, ""), "hex");
  const expected = createHmac("sha256", key)
    .update(timestamp).update(".").update(rawBody).digest("hex");

  const a = Buffer.from(expected, "utf8");
  const b = Buffer.from(presented, "utf8");
  if (a.length !== b.length || !timingSafeEqual(a, b)) return "签名不匹配";

  const now = Date.now();
  for (const [sig, at] of seen) if (now - at > TOLERANCE_SECONDS * 1000) seen.delete(sig);
  if (seen.has(presented)) return "该请求已投递过";
  seen.set(presented, now);

  return null;
}
```

用 Go 写的 handler 可以直接调用 Multica 仓库里的 `service.VerifyHookSignature`——这个方案是导出的，两侧实现完全一致。

## 应答

- 返回 `2xx`。其他状态一律记为失败，`event` 触发时还会计入熔断器。
- 响应体必须是 JSON，或者为空。空响应体表示调用成功但没有输出。
- 响应最多读取 1 MiB。返回一 GB 的 hook 会失败，而不是拖垮宿主。
- 在 `timeout_ms` 内应答（默认 10 秒，最大 30 秒）。耗时工作应该放到回调里，而不是塞进响应。
- 不要回显内部错误文本。你返回什么由宿主分类，回显内部信息是把自己的配置泄露进别人日志的常见方式。

对 `ui`、`manual`、`agent` 调用，你的 JSON 响应体会作为 `result.output` 回到调用方。对 `event` 调用没有人在等，响应体会被丢弃。

### 拒绝得体面一点

只会成功的 hook 是简单情况。当业务规则说"不行"时，请说清楚为什么：

```json
{ "error": "发布 d-4802 已过去 380 分钟，回滚窗口是 60 分钟" }
```

如果这应当计为失败就配非 2xx 状态；如果拒绝本身是一个合法答案，就返回 `200`。拿到理由的智能体能据此调整；拿到一个空洞失败的智能体只会盲目重试。

## 回调

每个请求都带 `callback_token` 和 `callback_url`。两者合起来，让你的 handler 在工作过程中可以使用 [Action API](/plugins/reference#action-api)：

```js
const issue = await fetch(`${body.callback_url}/issues/${body.issue_id}`, {
  headers: { Authorization: `Bearer ${body.callback_token}` },
}).then((r) => r.json());
```

需要了解的性质：

- **作用于一次调用，而不是一次请求。** 读任务再评论就是两次请求，这是"对读到的内容做点什么"的 handler 的下限。
- **是分钟级，不是小时级。** 签发后 5 分钟过期，且你的 handler 一应答，Multica 就立即吊销它。用完即弃，不要存起来。
- **收窄到本次调用相关的那个任务。** 访问别的任务会得到 `404`。
- **身份在派发时就已确定。** `ui`/`manual` 回调以触发者的身份写入，`agent` 回调以该智能体的身份写入，`event` 回调以插件的身份写入。handler 不能选择以别人的身份写入。
- **它的 scope 就是该安装的 scope**，绝不会更宽。

### 回调不够用时

如果你确实需要长期访问——比如一个夜间对账任务——请使用与签名密钥一起签发的**安装 token**（`mpi_…`）。它不会过期，始终以插件身份行事，并以哈希形式存储，因此 `admin` 弄丢了只能轮换而不能找回。优先用回调：它被限制在一次调用和一个任务内。

## 可靠性与限额

| 项目 | 取值 |
| --- | --- |
| 默认超时 | 10 秒（`timeout_ms`，100–30000） |
| 响应体大小 | 1 MiB |
| 频率限制 | 每个 hook 每分钟 120 次，按尝试次数计 |
| 事件重试 | 共 3 次，退避 2 秒、4 秒 |
| 熔断器 | 5 分钟内失败 5 次即打开，事件投递暂停到窗口滚过 |
| 签名时间容差 | 5 分钟 |
| callback token 有效期 | 5 分钟，调用结束即吊销 |
| 调用记录保留 | 7 天 |

**refused 不会重试。** 被停用、超出 scope 或触发频率限制的 hook 已经得到了答复，重试只是白白消耗额度。超时和接口故障只在 `event` 触发方式下重试。

熔断器只作用于 `event` 投递。成员或智能体调用 hook 时仍会真正尝试一次并拿到真实错误，因为他们在等结果。

## 查看 hook 活动

每次尝试都会被记录，并在 **设置 → Plugins** 中按安装展示：hook key、触发方式、事件类型、状态、第几次尝试、耗时和脱敏后的错误。状态取值为 `ok`、`failed`、`timeout`、`refused`。

请求体从不存储，所以这份日志回答的是"发生了什么、发生了多少次"，而不是"发出去的内容是什么"。错误文本只保留宿主自己的描述，远端提供的内容会被剥离——否则一个回显入参的接口就能把任务内容写进一张没有删除路径的表里。

记录保留 7 天后清理。没有任何逻辑会读取比熔断器和频率限制窗口（都只看几分钟）更老的记录。

## `mcp` transport

`http` hook 声明的是一个 `admin` 读过并批准的接口。而 MCP 服务器在运行时自行决定工具列表，并且随时可以变——那样"安装这个插件"就成了对"这台服务器下周提供什么就跑什么"的长期授权。

因此多了一步审批。对于 `"transport": { "type": "mcp", "url": "https://metrics.example.com/mcp" }` 的 hook：

1. `admin` 打开该 hook 的审批面板，Multica 探测服务器当前提供的工具。探测本身不采纳任何东西。
2. `admin` 勾选允许智能体使用的工具。每个都按**名称加 schema 摘要**固定下来。
3. 智能体只能调用这些。之后新增的工具不会被自动采纳；schema 发生漂移的工具会停止被调用。

安装插件不是授权，批准工具才是。在有人批准之前，`mcp` hook 什么也不贡献。

要向你自己的 MCP 服务器认证，声明一个名为 `<hook_key>_credential` 的 secret 配置项。它的值会作为 `Authorization` 头发送，且只在使用的那一刻解密：

```json
"config": {
  "metrics_credential": { "type": "secret", "label": "Metrics MCP server token" }
}
```

对应 key 为 `metrics` 的 hook。插件的 MCP 服务器挂掉不会让智能体的任务失败——该连接是可选的，智能体仍能继续处理任务。

## 本地开发

hook URL 必须是 HTTPS，所以本地 handler 需要证书。用两个运维配置把 Multica 指过去：

```bash
export MULTICA_PLUGIN_DEV_ORIGINS=https://127.0.0.1:8788
export MULTICA_PLUGIN_DEV_CA=/path/to/your-dev-ca.pem
```

前者列出豁免公网地址校验的源；后者只为这些源额外信任一个 CA。两者都不会关闭证书校验，也都不会放宽 `net:`——hook 仍然无法访问 `admin` 未批准的主机，所以也要声明 `net:127.0.0.1`。见[分发与本地开发](/plugins/distribution#本地开发)。
