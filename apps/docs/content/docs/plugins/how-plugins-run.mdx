Read this page once before designing a plugin. Most surprises later — why a comment carries someone's name, why a scope was refused, why an event hook cannot write as a member — follow from what is here.

## Where your code runs

Multica never executes plugin code. There are exactly two places it runs:

- **In the user's browser**, as a surface: a script inside a sandboxed iframe on the page the user is already looking at.
- **On your own server**, as a hook handler: an ordinary HTTPS endpoint Multica sends a signed `POST` to.

There is no third place. Nothing is uploaded, nothing is sandboxed server-side, and no plugin process exists on Multica's infrastructure. That single decision explains most of the architecture below.

## The surface: an iframe with no credential

A surface is mounted with `sandbox="allow-scripts"` and deliberately **not** `allow-same-origin` — the pairing the HTML spec calls out as defeating the sandbox. The document therefore has an opaque origin, with the consequences you should design around:

- No cookies, no `localStorage`, no `sessionStorage`, no `IndexedDB`.
- No access to the embedding page, and no shared storage between two plugins on the same page.
- `Origin: null` on any request the surface makes itself.
- A Content-Security-Policy your plugin did not write, derived from its granted `net:` scopes.

The document itself is generated by Multica, not by you. That is what makes the CSP enforceable: a policy is set by whoever emits the document, so if your server emitted it, the scopes an admin approved would be a claim nobody checks. Your `entry` script is loaded into that generated document from your own origin.

### The bridge

Since the frame holds no credential, it cannot call Multica directly. It asks the host page instead:

```
surface  ──postMessage──▶  host page  ──user's session──▶  Multica API
        ◀──MessagePort───              ◀──────────────────
```

The handshake is started by the guest, not the host. The surface posts `multica:plugin-surface-ready` to its parent, repeatedly until answered; the host replies with `multica:plugin-bridge-init` carrying one `MessagePort` and the current theme tokens. From then on both sides talk only over that port.

Identity is bound by the port, never by `event.origin`: every sandboxed frame reports the origin `"null"`, so comparing origins would authenticate nothing. The host creates one channel per iframe and only listens on its own end, so "which plugin sent this" is answered by which channel it arrived on. The SDK mirrors the check on its side — it accepts a port only from `window.parent`, and only the first one — because sibling frames on the same page can reach each other through indexed access and could otherwise pose as the host.

The SDK handles all of this. It is described here because the failure modes are invisible otherwise: a blank panel is what both a missed handshake and a version mismatch look like.

### What that buys

Every Action API call from a surface is performed by the host on the signed-in user's own session. So a plugin can never do more than the person looking at it, and there is no token in the frame to leak.

## The hook: your server, called by Multica

A hook is the only direction in which Multica calls out. Because the request leaves Multica's infrastructure, the checks are about the destination rather than the caller:

1. The host must be covered by a `net:` scope the admin granted — exact host, never a suffix.
2. The address must resolve publicly at dial time, and the dialer re-resolves so a hostname that flips to a private IP after validation cannot be used to reach inside the network.
3. Redirects are refused; a `302` would replay the signed body and the callback token to wherever it pointed.
4. The body is signed, so your handler can distinguish Multica's call from anyone else's.

Hooks are reached from four call sites. Only `event` is asynchronous, and it never blocks anything the host is doing.

| Trigger | Who initiates | Blocking |
| --- | --- | --- |
| `ui` | Your own surface, via `multica.hooks.invoke()` | Blocks that panel's request only |
| `manual` | A person, from the issue actions menu or command palette | Blocks that menu action only |
| `agent` | An agent that chose to call your hook as a tool | Blocks that tool call only |
| `event` | Multica, on a product event | Never — dispatched onto a worker pool |

`event` never blocking is structural, not tuning. The event bus runs its listeners inline on the goroutine of the request that published, so a hook dialled from there would put your server on the critical path of creating an issue.

<Callout type="info">
There is deliberately no "before every agent turn" or "after every agent turn" hook. A hook that must run around the product's main loop is a third party holding it open. Agents reach hooks by *choosing* to call one as a tool — a call they can also decline.
</Callout>

## Identity: who a call acts as

This is the part worth internalising. A plugin does not pick an identity; the identity follows from how the call arrived.

| Path in | Acts as | Writes are attributed to |
| --- | --- | --- |
| Surface, over the bridge | The signed-in member | That member, marked `via_plugin_id` |
| Hook callback token from a `ui` or `manual` invocation | The person who triggered it | That member, marked `via_plugin_id` |
| Hook callback token from an `agent` invocation | The agent | That agent |
| Hook callback token from an `event` invocation | The plugin | The installation itself |
| Install token (standing credential) | The plugin | The installation itself |

Two consequences to design around:

- **An event hook cannot write as a person.** It has nobody behind it, and borrowing the last member who happened to touch the issue would be a lie the audit trail cannot undo. Endpoints that require a member — `storage:user`, invoking a `ui`/`manual` hook — refuse a plugin-actor call with a `403` that says so.
- **A member callback is only as good as that membership today.** The member is re-checked when the token is redeemed, so revoking someone's access takes effect on a token already in flight.

## The three checks on every Action API call

In this order:

1. The installation exists in this workspace and is **enabled**.
2. The installation was granted the scope this endpoint needs.
3. The signed-in user may touch this resource — enforced by the ordinary resource loaders, not by anything plugin-specific.

Check 3 is what makes the model safe: a plugin can never let someone do what they could not already do themselves. Checks 1 and 2 bound the plugin *below* that ceiling. The workspace always comes from the installation, never from a client header, so an installation cannot be aimed at a workspace it was never installed in.

Disabling a plugin takes effect immediately at check 1 — a surface left open in a stale tab stops working even though nothing re-rendered.

## Lifecycle

| Step | What happens |
| --- | --- |
| **Preview** | The manifest is fetched and parsed. Nothing is written. The response drives the consent screen and, on an upgrade, lists newly requested scopes. |
| **Install** | An installation row stores the canonical manifest snapshot, the granted scopes, and the source URL. Skill resources are fetched and written in the same transaction. |
| **Configure** | Values are validated against the stored manifest schema. Plain values go on the installation; `secret` values go to a separate encrypted table. |
| **Upgrade** | Installing the same `key` again replaces the snapshot. Config fields the new manifest dropped are pruned, including orphaned secrets, in one transaction. |
| **Disable** | Every contribution stops immediately. Storage, secrets, and configuration are kept, so re-enabling is not a reinstall. |
| **Uninstall** | The installation, its storage, its secrets, its invocation records, and the skills it contributed are deleted together. |

The manifest that matters at runtime is always the **stored snapshot**, never what your URL serves today. If you repoint a hook's endpoint, that takes effect only after somebody reinstalls — which re-runs consent. Surface code and hook handler behaviour are outside the snapshot and change as soon as you deploy them.
