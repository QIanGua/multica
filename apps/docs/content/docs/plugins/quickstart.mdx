This page builds one plugin twice: first the smallest thing that renders (a panel), then the same plugin with a hook your own server answers.

You need a workspace where you are an `admin`, plugins enabled for that deployment, and somewhere to serve two static files over HTTPS.

## 1. Two files

A plugin is a manifest plus whatever it points at. Put both in one directory.

```
hello-panel/
  multica.plugin.json
  ui/main.js
```

`multica.plugin.json`:

```json
{
  "manifest_version": 1,
  "key": "com.example.hello-panel",
  "name": "Hello Panel",
  "description": "Reads the current issue and stores a private note.",
  "version": "1.0.0",
  "author": { "name": "Your Name", "url": "https://example.com" },
  "scopes": ["issues:read", "comments:write", "storage:user"],
  "contributes": {
    "surfaces": [
      {
        "key": "hello",
        "type": "issue_panel",
        "name": "Hello",
        "entry": "ui/main.js",
        "platforms": ["web", "desktop"]
      }
    ]
  }
}
```

Three things about this file are easy to get wrong:

- `key` must be a reverse-DNS namespace — at least two dot-separated segments. It identifies your plugin forever; installing a manifest whose `key` matches an existing installation is an *upgrade*, not a second install.
- `version` must be valid semantic versioning.
- `entry` is a path relative to the manifest URL, and it must be a `.js` or `.mjs` **script**, not an HTML page. Multica generates the document your script runs in — that is what lets it attach a CSP derived from your scopes.

## 2. The entry script

`ui/main.js` is a plain ES module. In production, import the SDK:

```js
import { multica } from "@multica/plugin-sdk";

const context = await multica.context.get();
const issue = await multica.issue.get();

document.getElementById("root").innerHTML = `
  <div style="padding:12px 14px; display:grid; gap:10px">
    <div style="color:var(--muted-foreground)">
      ${context.user.name} · ${context.workspace.name}
    </div>
    <div style="font-weight:600">${issue.title}</div>
    <input id="note" placeholder="A note only you can see"
      style="padding:6px 8px; border:1px solid var(--border);
             border-radius:var(--radius,6px);
             background:var(--background); color:var(--foreground)">
    <button id="save">Save</button>
  </div>`;

const note = document.getElementById("note");
note.value = (await multica.storage.user.get("note")) ?? "";
document.getElementById("save").onclick = () =>
  multica.storage.user.set("note", note.value);

// The frame does not auto-size. Ask for the height you need.
multica.ui.resize(document.body.scrollHeight + 16);
```

The SDK has zero runtime dependencies, so bundling it produces a single file you can serve statically. If you would rather ship no build step at all, `examples/plugins/hello-panel/ui/main.js` in the Multica repository inlines a minimal bridge client that does the same thing in about 40 lines.

<Callout type="warn">
Your surface runs with an opaque origin. `localStorage`, `sessionStorage`, and cookies throw or read as empty — use `multica.storage`, which is server-side and survives the frame. See [Surfaces](/plugins/surfaces) for the full list of constraints.
</Callout>

## 3. Serve both files

The manifest and everything it references must be served from the same directory over public HTTPS, because `entry` resolves relative to the manifest URL and **Multica never re-hosts plugin code**. Any static host works: object storage, a CDN, GitHub Pages, your own server.

```
https://plugins.example.com/hello-panel/multica.plugin.json
https://plugins.example.com/hello-panel/ui/main.js
```

For iteration without publishing, see [local development](/plugins/distribution#local-development). Loopback HTTP is accepted for a surface entry, which is enough to run a panel off a local static server.

## 4. Install it

In the workspace, open **Settings → Plugins → Install** and paste the manifest URL.

Installation is deliberately two steps. The first fetches and parses the manifest and shows you what it declares, including every scope; nothing is written. The second creates the installation, and it must consent to exactly the manifest's scope list — partial consent is refused, because a plugin missing half its permissions is broken in ways nobody can see.

Open any issue. Your panel renders under **Plugins**.

## 5. Add a hook

A surface can only do what the person looking at it can do. To reach your own service, add a hook — a capability Multica calls on your server.

Two manifest changes: declare the host you will call, and declare the hook.

```json
{
  "scopes": [
    "issues:read",
    "comments:write",
    "storage:user",
    "net:hooks.example.com"
  ],
  "contributes": {
    "hooks": [
      {
        "key": "triage_issue",
        "name": "Triage this issue",
        "description": "Sends the issue title and description to our triage service and posts the suggested owner and priority back as a comment.",
        "input_schema": {
          "type": "object",
          "properties": { "reason": { "type": "string" } }
        },
        "triggers": ["ui", "manual", "event"],
        "events": ["issue.created"],
        "transport": { "type": "http", "url": "https://hooks.example.com/triage" },
        "timeout_ms": 8000
      }
    ]
  }
}
```

The `net:hooks.example.com` scope is not optional decoration: a hook whose transport URL is not covered by a declared `net:` scope fails manifest validation. It is an exact host match, so `api.hooks.example.com` needs its own scope.

Those three triggers are the same hook reached three ways, and the difference decides whose name the resulting writes carry:

| Trigger | Where it comes from | Blocks | Writes are attributed to |
| --- | --- | --- | --- |
| `ui` | A button your surface draws, via `multica.hooks.invoke()` | Only that panel | The person who clicked |
| `manual` | The issue actions menu and command palette, rendered by Multica | Only that menu | The person who picked it |
| `event` | Automatic, on `issue.created` | Never | The plugin itself |

## 6. Answer the hook

Multica sends your endpoint a signed `POST`. A handler must verify the signature **against the raw bytes, before parsing** — re-serializing the JSON and signing that instead is the classic way to make valid signatures fail and invalid ones pass.

```js
import { createHmac, timingSafeEqual } from "node:crypto";

const SECRET = process.env.MULTICA_SIGNING_SECRET.replace(/^whsec_/, "");
const TOLERANCE_SECONDS = 5 * 60;

function verify(rawBody, headers) {
  const timestamp = headers["x-multica-timestamp"];
  const presented = String(headers["x-multica-signature"] ?? "").replace(/^v1=/, "");
  if (!timestamp || !presented) return "missing signature headers";

  const drift = Math.abs(Math.floor(Date.now() / 1000) - Number(timestamp));
  if (!Number.isFinite(drift) || drift > TOLERANCE_SECONDS) return "stale timestamp";

  const expected = createHmac("sha256", Buffer.from(SECRET, "hex"))
    .update(timestamp).update(".").update(rawBody).digest("hex");

  const a = Buffer.from(expected, "utf8");
  const b = Buffer.from(presented, "utf8");
  if (a.length !== b.length || !timingSafeEqual(a, b)) return "signature mismatch";
  return null;
}
```

The signing secret is shown once, next to the install token, when an admin rotates the plugin's token in **Settings → Plugins**. It is stable for an installation.

Each request also carries `callback_token` and `callback_url`, so your handler can call the [Action API](/plugins/reference#action-api) back for the few minutes it is valid:

```js
const issue = await fetch(`${body.callback_url}/issues/${body.issue_id}`, {
  headers: { Authorization: `Bearer ${body.callback_token}` },
}).then((r) => r.json());

await fetch(`${body.callback_url}/issues/${body.issue_id}/comments`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${body.callback_token}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ content: `Triage: **high**, owner **platform**.` }),
});
```

You do not choose the identity those writes land under — it was decided when the hook was dispatched. See [Hooks](/plugins/hooks) for the full request format, retry schedule, and rate limits.

## 7. Reinstall to publish a change

An installation stores the manifest snapshot the admin consented to. Changing the file you serve has no effect until somebody installs the new URL again, which re-runs the consent screen and highlights any newly requested scopes. Surface code and hook endpoints, by contrast, are yours: those change the moment you deploy them.

## Working examples

The Multica repository ships four, in `examples/plugins/`:

| Example | What it demonstrates |
| --- | --- |
| `hello-panel` | The reference surface: context, issue read, comment write, per-member storage, resize |
| `release-checklist` | Config-driven UI — the admin edits the checklist once, every issue keeps its own state |
| `triage-notify` | The hook engine, all three host-driven triggers, and a reference handler with signature verification and replay protection |
| `deploy-sentinel` | The shape of a real plugin: four triggers, both transports, a skill, and business rules that refuse things |
