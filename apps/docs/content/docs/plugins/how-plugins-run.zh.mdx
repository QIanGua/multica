设计插件前先读一遍这一页。之后大部分"意外"——评论为什么署了某个人的名字、scope 为什么被拒、event hook 为什么不能以成员身份写入——都源自这里的内容。

## 你的代码在哪里运行

Multica 从不执行插件代码。它只在两个地方运行：

- **用户的浏览器里**，作为 surface：运行在用户正在查看的页面上、一个沙箱 iframe 中的脚本。
- **你自己的服务器上**，作为 hook handler：一个普通的 HTTPS 接口，Multica 向它发送带签名的 `POST`。

没有第三个地方。没有上传，没有服务端沙箱，Multica 的基础设施上不存在任何插件进程。下面的架构大多由这一个决定推导而来。

## surface：不持凭证的 iframe

surface 以 `sandbox="allow-scripts"` 挂载，并刻意**不带** `allow-same-origin`——HTML 规范明确指出这两者同时出现会让沙箱失效。因此这个文档拥有不透明源，你需要围绕这些后果来设计：

- 没有 cookie、`localStorage`、`sessionStorage`、`IndexedDB`。
- 无法访问外层页面，两个插件之间也不共享任何存储。
- surface 自己发出的请求带 `Origin: null`。
- 一份不是你写的 Content-Security-Policy，由授予的 `net:` scope 推导而来。

文档本身由 Multica 生成，而不是你。这正是 CSP 可执行的原因：策略由生成文档的一方设定，如果文档由你的服务器输出，`admin` 批准的 scope 就成了一句没人核验的声明。你的 `entry` 脚本从你自己的源加载进这个生成的文档。

### bridge

由于 iframe 不持有凭证，它无法直接调用 Multica，只能向宿主页面请求：

```
surface  ──postMessage──▶  宿主页面  ──用户会话──▶  Multica API
        ◀──MessagePort───            ◀────────────
```

握手由访客端发起，而不是宿主端。surface 反复向父窗口投递 `multica:plugin-surface-ready` 直到得到回应；宿主回以 `multica:plugin-bridge-init`，其中携带一个 `MessagePort` 和当前主题 token。此后双方只通过这个 port 通信。

身份由 port 绑定，永远不看 `event.origin`：所有沙箱 iframe 的源都是字符串 `"null"`，比较源等于什么都没验证。宿主为每个 iframe 建一条独立通道，且只监听自己这一端，因此"这条消息是哪个插件发的"由它从哪条通道到达来回答。SDK 这一侧做了对称的检查——只接受来自 `window.parent` 的 port，且只接受第一个——因为同页面的兄弟 iframe 可以通过下标访问互相投递消息，否则就能冒充宿主。

这些都由 SDK 处理。之所以写在文档里，是因为它的失败形态是不可见的：握手错过和版本不匹配，看起来都只是一个空白面板。

### 这换来了什么

surface 发出的每次 Action API 调用，都由宿主用当前登录用户自己的会话执行。所以插件永远不可能超出正在使用它的人的权限，而且 iframe 里没有任何可泄露的 token。

## hook：由 Multica 调用你的服务器

hook 是 Multica 唯一向外调用的方向。因为请求会离开 Multica 的基础设施，所有检查都围绕目标地址展开：

1. 目标主机必须被 `admin` 授予的 `net:` scope 覆盖——精确匹配，绝不做后缀匹配。
2. 拨号时地址必须解析为公网地址，且拨号器会重新解析，因此校验之后才切换到内网 IP 的域名也无法用来访问内部网络。
3. 拒绝重定向；`302` 会把带签名的请求体和 callback token 重放到它指向的任意地方。
4. 请求体带签名，你的 handler 能据此区分 Multica 的调用和别人的调用。

hook 有四个调用入口。只有 `event` 是异步的，它永远不会阻塞宿主正在做的事。

| 触发方式 | 发起者 | 阻塞 |
| --- | --- | --- |
| `ui` | 你自己的 surface，经 `multica.hooks.invoke()` | 仅阻塞该面板的这次请求 |
| `manual` | 成员，从任务操作菜单或命令面板 | 仅阻塞该菜单操作 |
| `agent` | 选择把你的 hook 当工具调用的智能体 | 仅阻塞该次工具调用 |
| `event` | Multica，在产品事件发生时 | 从不——派发到工作线程池 |

`event` 不阻塞是结构性的，不是性能调优。事件总线是同步的，监听器直接跑在发布事件那个请求的协程上，所以从那里拨号会把你的服务器放到"创建任务"这条关键路径上。

<Callout type="info">
Multica 刻意没有"智能体每轮之前/之后"的 hook。绕着产品主循环运行的 hook，等于让第三方一直握着这条主循环。智能体访问 hook 的方式是**主动选择**把它当工具调用——同样也可以选择不调用。
</Callout>

## 身份：这次调用以谁的名义发生

这是最值得记住的部分。插件不能挑选身份；身份由调用是怎么进来的决定。

| 入口 | 身份 | 写入归属 |
| --- | --- | --- |
| surface，经 bridge | 当前登录成员 | 该成员，并标记 `via_plugin_id` |
| `ui` / `manual` 调用下发的 callback token | 触发的人 | 该成员，并标记 `via_plugin_id` |
| `agent` 调用下发的 callback token | 该智能体 | 该智能体 |
| `event` 调用下发的 callback token | 插件 | 该安装本身 |
| 安装 token（长期凭证） | 插件 | 该安装本身 |

两个需要围绕它设计的结论：

- **event hook 不能以某个人的身份写入。** 它背后没有人，而借用"最近碰过这个任务的成员"是一句审计日志无法纠正的谎言。需要真实成员的接口——`storage:user`、调用 `ui`/`manual` hook——会对插件身份的调用返回 `403` 并说明原因。
- **成员回调的有效性以"今天"为准。** token 兑换时会重新检查成员资格，因此撤销某人的权限，对已经在途的 token 同样立即生效。

## 每次 Action API 调用的三道检查

按顺序：

1. 该安装存在于这个工作区，且处于**启用**状态。
2. 该安装被授予了这个接口所需的 scope。
3. 当前登录用户有权访问该资源——由普通的资源加载逻辑执行，而不是插件专有的一套。

第三道检查是整个模型安全的关键：插件永远不能让某人做他本来做不到的事。前两道则把插件限制在这个上限**之下**。工作区始终来自安装记录而非客户端请求头，因此无法把一个安装指向它从未被安装过的工作区。

停用插件在第一道检查处立即生效——留在旧标签页里的 surface 会立刻失效，即使那个页面从未重新渲染。

## 生命周期

| 步骤 | 发生了什么 |
| --- | --- |
| **预览** | 抓取并解析 manifest，不写入任何数据。响应用于渲染授权页面；若是升级，还会列出新增的 scope。 |
| **安装** | 安装记录保存规范化的 manifest 快照、已授予的 scope 和来源 URL。skill 资源在同一个事务中抓取并写入。 |
| **配置** | 依据已存储的 manifest schema 校验取值。普通值存在安装记录上，`secret` 值进入独立的加密表。 |
| **升级** | 再次安装相同 `key` 会替换快照。新 manifest 已删除的配置项会被清理，包括残留的 secret，全部在一个事务内完成。 |
| **停用** | 所有贡献立即停止。存储、secret 和配置都保留，因此重新启用不等于重装。 |
| **卸载** | 安装记录、它的存储、secret、调用记录以及它贡献的 skill 一并删除。 |

运行时生效的永远是**已存储的快照**，而不是你的 URL 今天返回什么。如果你改了某个 hook 的接口地址，要等有人重新安装才会生效——那正好会重新走一遍授权。相对地，surface 代码和 hook handler 的行为不在快照里，部署即生效。
